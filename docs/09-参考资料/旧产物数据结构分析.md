# 旧产物数据结构分析

基于旧系统（位于 `旧产物/` 目录）的分析，以下是关键数据结构和业务逻辑的总结。

## 1. 旧系统概况

### 1.1 技术栈（推测）
- **后端**: Python + Flask/Django
- **数据库**: MySQL (端口 3307)
- **前端**: 浏览器端验收测试
- **架构**: Nginx (端口 8080) 作为网关

### 1.2 核心业务模块

从 `v83_acceptance.py` 和 `v82_health.py` 等文件中可以看出：

1. **试卷识别与拆题**
   - PDF 上传和解析
   - AI 自动拆题
   - 人工编辑草稿
   - 确认入库（幂等性）

2. **题库管理**
   - `questions` 表：存储题目
   - `paper_ai_recognition_drafts` 表：AI 识别草稿
   - `exam_subject_id`: 科目关联（如 subject_id=8）

3. **版本管理**
   - 版本验收脚本（v82, v83）
   - 健康检查机制
   - 数据清理脚本

## 2. 数据库结构（推测）

### 2.1 核心表

```sql
-- 题目表
CREATE TABLE questions (
    id INT PRIMARY KEY AUTO_INCREMENT,
    exam_subject_id INT,           -- 科目ID
    content_source VARCHAR(50),    -- 'ai_import', 'manual'
    question_no VARCHAR(20),       -- 题号
    content TEXT,                  -- 题目内容
    answer TEXT,                   -- 答案
    score DECIMAL(10,2),          -- 分值
    created_at TIMESTAMP,
    updated_at TIMESTAMP
);

-- AI 识别草稿表
CREATE TABLE paper_ai_recognition_drafts (
    id INT PRIMARY KEY AUTO_INCREMENT,
    exam_subject_id INT,
    pdf_path VARCHAR(500),
    recognition_result JSON,       -- AI 识别结果
    status VARCHAR(20),           -- 'draft', 'confirmed'
    version INT,                  -- 版本号
    created_at TIMESTAMP,
    updated_at TIMESTAMP
);

-- 考试科目表
CREATE TABLE exam_subjects (
    id INT PRIMARY KEY AUTO_INCREMENT,
    exam_id INT,
    subject_id INT,
    full_score DECIMAL(10,2),
    created_at TIMESTAMP
);
```

### 2.2 关键字段映射

| 旧系统字段 | 新系统对应 | 说明 |
|---|---|---|
| `exam_subject_id` | `exam_subjects.id` | 考试科目关联 |
| `content_source='ai_import'` | `source_system='legacy_ai'` | 数据来源标识 |
| `paper_ai_recognition_drafts` | - | 新系统不复用草稿机制 |

## 3. 业务流程

### 3.1 试卷处理流程

```text
1. PDF 上传
   ↓
2. AI OCR 识别
   ↓
3. 生成草稿（drafts 表）
   ↓
4. 人工编辑框选
   ↓
5. 确认入库（questions 表）
   ↓
6. 版本验收测试
```

### 3.2 数据迁移关键点

1. **幂等性处理**
   - 旧系统有 `content_source` 字段标识来源
   - 新系统需要 `external_id` + `source_system` 确保幂等

2. **状态流转**
   - 旧系统：draft → confirmed → published
   - 新系统：通过 `status` 字段管理

3. **版本追踪**
   - 旧系统有版本号机制
   - 新系统需要 `source_updated_at` + `source_hash` 检测变化

## 6. 关键发现

### 6.1 数据质量问题

1. **外键约束**
   - 旧系统可能缺少严格外键
   - 迁移时需要数据清洗

2. **字符编码**
   - MySQL 可能是 utf8mb3
   - 迁移到 PostgreSQL UTF-8

3. **时间戳**
   - 旧系统可能混用本地时间和 UTC
   - 新系统统一使用 UTC

### 6.2 业务逻辑复用

可以复用的逻辑：
- ✅ 试卷拆题流程
- ✅ 题目版本管理
- ✅ 数据来源标识

需要重写的逻辑：
- ❌ 权限控制（新系统更严格）
- ❌ AI 模型调用（新系统统一 ModelGateway）
- ❌ 前端界面（React 重写）
