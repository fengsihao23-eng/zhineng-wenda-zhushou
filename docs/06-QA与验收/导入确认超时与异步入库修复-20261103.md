# 导入「确认入库」超时与异步入库修复 · 2026-11-03

## 1. 结论

教师/学生名单导入的「确认入库」已改为**后台任务 + 前端轮询**。确认请求不再等待 bcrypt 和逐行写入，生产隔离环境实测：

| 操作 | 修复前 | 修复后 |
|---|---|---|
| 200 行学生确认 | 约 55 秒 | **0.06–0.08 秒**返回 `running` |
| 重复点击确认 | 再跑一遍，排队 | **0.11–0.3 秒**返回同一批次 |
| 1,448 行学生确认 | **372.9 秒**（前端/网关早已断开） | 立即返回，后台继续写入 |
| 200 行后台写入 | — | 18.2–19.1 秒完成 |
| 确认请求失败提示 | 「操作失败，请重试」 | 明确显示「正在整批入库，已等待 N 秒」；失败可重试 |

## 2. 根因（修正上一版判断）

真正触发失败的不是 axios：家长/教师导入页走的是原生 `fetch`，没有 30 秒超时。**限制来自 nginx**：

```nginx
location ^~ /api/ {
    proxy_read_timeout 60s;
    proxy_send_timeout 60s;
}
```

同时每个账号的初始密码要单独跑 `bcrypt_sha256`，容器内实测 **276 ms/个**；API 容器 CPU 限额 **1.25 核**。因此：

- 教师 286 行 ≈ 79 秒 → 超过 60 秒，浏览器收到网关断开，显示「操作失败」
- 学生 1,448 行 ≈ 320–373 秒 → 必然超时
- 第二次点教师能成功：第一次其实已提交，第二次命中 `succeeded` 幂等返回（0.1 秒）
- 学生连点三次：后两次在批次行锁上排队，每次前端仍先收到超时

数据本身没有错：生产库当时已正确写入 1,448 名学生、286 名教师，用户名唯一、无重复。

## 3. 改动内容

### 后端

- `apps/api/app/services/roster_workbench.py`
  - `confirm()` 只做完整复校验（预检、疑似重复、保留/放弃选择），把批次置为 `running` 后立即返回；
  - 新增 `execute_import()` 后台工人：独立事务、失败整体回滚、成功后写 `succeeded`、异常写 `failed` + `failed_reason`；
  - 只有真正把批次从 `ready/failed` 推进到 `running` 的请求才返回 `_queued`，重复请求不会重复入队；
  - 教师密码哈希改为与学生的有界并发（信号量 4），教师 286 行由约 79 秒降到约 20 秒；
  - `running` 超过 30 分钟视为进程重启遗留，允许重新提交（崩溃场景不会产生半批数据，因为写在一个事务里）；
  - 新增 `progress_view()`：轮询只返回状态与进度摘要，**不再每次下发 1,448 行原始名单**。
- `apps/api/app/services/teacher_changes.py`
  - 教师「资料变更专属任务」同样改为异步：确认时校验对应关系、身份确认、锁定教师ID，批次置 `running`、任务置 `running` 后立即返回；
  - 新增 `execute_task_import()`：单事务改写教师档案、角色、任课关系与快照版本，失败回滚并把任务退回 `pending`；
  - 任务批次失败可重试，不会出现部分教师已更新、部分未更新。
- `apps/api/app/api/v1/endpoints/roster.py`
  - `confirm` 注入 `BackgroundTasks`，按 `_queued` 类型启动学生/教师 worker；
  - `GET /roster/imports/{id}?progress=true` 返回轻量进度。
- `apps/api/app/main.py`
  - 启动时扫描仍为 `running` 的批次并自动恢复执行。部署/重启中断的批次不再永久卡住；worker 行锁保证多进程下只有一方写入。

### 前端

- `shared.tsx`：新增 `pollRosterImport` / `useImportPolling` / `ImportRunning` / `ImportFailure`；
- `StudentWorkbench.tsx`、`TeacherWorkbench.tsx`：
  - 确认后状态为 `running` 时每 1.5 秒轮询一次，显示已等待秒数；
  - 终态后再拉一次完整回执（无重复下载大名单）；
  - `failed` 显示服务端原因并提供「重试入库」；
  - 重新打开历史批次时，若仍在 `running` 会自动继续轮询；
  - 轮询期间禁止重复提交。

### 测试

- `tests/test_roster_workflows.py`：`confirm` helper 等待终态；中途写入失败改为断言 `failed`、零写入；PostgreSQL 并发用例改为断言只有一个请求入队且只写一次。
- `tests/test_roster_student_requirements.py`：补充 compact 确认轮询、`progress=true` 不返回 `rows/columns`。

结果：名单相关 **41 项通过**；全套 API **350 项通过**，2 项失败为本地 DeepSeek 余额 402（与本改动无关）；前端 `tsc`、`eslint`、31 项单测、生产构建通过。

## 5.1 部署期间的实际中断与恢复

18:13（北京时间）部署 `20261103b` 时，用户恰好确认了一个 1,481 行学生导入。API 重建导致原进程中的 worker 中断，批次停在 `running`。处理：

1. 用生产镜像 + 生产 `DATABASE_URL` 启动一次性容器，对同一批次执行 `execute_import`；
2. 约 2 分钟后写入完成：`succeeded`，1,481 条，学生总数 1,448 → 2,929；
3. 用户在此期间重试同一文件，产生第二个批次；因账号已被第一批写入，第二批复校验判定重复，状态 `invalid`，**未写入任何数据**，属于正确保护；
4. 随后加入启动自动恢复，避免再次出现「重启即卡住」。隔离环境模拟「进程停止后仍为 running」的批次，重启 API 后日志出现 `roster_imports_resumed count=1`，30 秒内批次转为 `succeeded`、100 行写入完成。
