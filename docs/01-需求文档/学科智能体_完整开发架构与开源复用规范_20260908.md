# 0. 最终结论

本项目**不是做一个“套 ChatGPT UI + PDF RAG”的聊天机器人**。

最终产品应当是：

> **以学校真实业务数据为事实底座，以学生身份和权限为边界，以成绩 / 排名 / 小题得分 / 诊断报告为动态上下文，以轻量 Agent + Tool Calling 为交互核心，后续再逐步接入教材知识库、错题、题库、知识点和个性化教学能力的“学生智能体”。**

一期必须先把下面这条链路做稳：

```text
学生登录
  ↓
身份 / 学校 / 班级 / 学生数据范围确认
  ↓
用户提问
  ↓
Student Context Builder
  ↓
轻量 Agent
  ↓
按需 Tool Calling
  ↓
真实成绩 / 排名 / 小题数据
  ↓
权益判断 BASIC / DIAGNOSIS
  ↓
模型生成简洁回答
  ↓
事实校验 / 越权检查
  ↓
流式返回
  ↓
会话 / Tool / Model Trace / Audit 落库
```

一期明确不做：

- 不上复杂 Multi-Agent 编排。
- 不让模型直接查 SQL。
- 不让模型自行决定能不能读取付费诊断数据。
- 不依赖 RAG 才能回答成绩问题。
- 不把全部历史成绩塞进 Prompt。
- 不让 LLM 计算成绩、排名、差值等确定性数值。
- 未购买诊断报告时，不允许模型推断“薄弱知识点、失分原因、学习问题”。
- 不因为参考 OpenTutor / Dify / RAGFlow 就把整个平台全搬进来。
- 不为了“架构漂亮”把现有学校业务能力全部重写。

# 1. 当前项目事实基线

现有系统已经具备或已有明确业务设计：

```text

    ↓
考务管理
    ↓
考试 / 试卷
    ↓

    ↓

    ↓
AI 拆题
    ↓

    ↓
人工审核 / 框选纠错
    ↓

    ↓
知识点绑定
    ↓
成绩 / 小题得分
    ↓

    ↓
```

已有资产包括：

- React + TypeScript 前端；
- 学生、教师、班级、考试、试卷、题库、知识点、成绩等业务；
- 试卷框选拆题；
- OCR / AI 结构化；
- 模型管理；
- Prompt 管理；
- Docker / Nginx；
- Redis；
- QA / Playwright 测试；
- 旧 MySQL 数据与接口；
- 学情分析报告能力。

因此新项目不是“从产品上重做一遍”，而是：

1. 建新的、清晰的 AI / Agent 技术底座；
2. 把旧系统已有业务通过 Adapter / Migration 接过来；
3. 学生侧先形成真实数据问答闭环；
4. 再逐步增加诊断、知识库和个性化教学。

# 2. 最新技术路线：新底座，但不做业务大爆炸重写

最新计划采用：

| 层 | 技术 |
|---|---|
| 前端 | React + TypeScript |
| 后端 | FastAPI |
| 数据库 | PostgreSQL |
| 向量 | pgvector（先装扩展，第一阶段不强依赖） |
| ORM | SQLAlchemy 2.x Async |
| Migration | Alembic |
| 数据校验 | Pydantic v2 |
| 缓存/队列 | Redis |
| 网关 | Nginx |
| 部署 | Docker Compose |
| QA | pytest + API test + Playwright |
| AI | Model Gateway + Prompt Registry + Tool Calling |
| Streaming | SSE 优先 |
| Observability | request_id / trace_id / agent_run_id / model_call_id |

### 2.1 新旧路线冲突怎么处理

旧接管文档曾建议“先保留 Flask + MySQL”。

最新阶段计划已经改成：

> React + FastAPI + PostgreSQL + pgvector。

因此实施时采用：

```text
旧系统 = 业务资产 + 数据源 + 迁移来源
新系统 = 新 AI / 学生智能体主线
```

不是直接删除旧系统。

建议迁移方式：

```text
Old MySQL / Old API
        │
        ├── Legacy Adapter
        │
        ├── Data Sync
        │
        └── Migration Jobs
                ↓
       New PostgreSQL
                ↓
        Student Agent
```

第一阶段允许新系统通过 Adapter 只读旧数据，避免“大迁库 + 大改接口 + Agent 新功能”同时发生。

它的 `context_builder.py` 做了几个非常正确的事情：

- Context 不在 API Router 内拼。
- Preference / Memory / RAG 可以并行加载。
- 不同类型 Context 有独立 budget。
- Context 太大时会 trim / compact。
- Context 是 AgentState 的一部分，而不是散落字符串。
- Context 获取失败时可降级，不一定让整轮对话失败。

**我们要借这个思想，但一期砍掉复杂度。**

本项目一期：

```text
OpenTutor
Preference + Memory + RAG + TeachingState + Assignment
                     ↓
我们的简化版
Identity + Exam + Score + Rank + QuestionLoss + DiagnosisEntitlement
```

# 11. BASIC / DIAGNOSIS 权益分层

这是一期最重要的产品规则之一。

## BASIC

允许读取：

- 学生自己的身份；
- 考试列表；
- 总分；
- 单科成绩；
- 班级排名；
- 年级排名；
- 历史趋势；
- 小题得分；
- 客观计算出的差值、得分率、排名变化。

不允许：

- 读取付费诊断报告；
- 自行推断薄弱知识点；
- 自行推断失分原因；
- 伪造学习建议所依据的诊断结论。

## DIAGNOSIS

在 BASIC 基础上额外允许：

- 读取已购买的对应诊断报告；
- 回答报告中的薄弱点；
- 回答报告中的优势；
- 回答报告中的失分原因；
- 回答报告中的建议；
- 回答报告中的诊断依据。

但：

> 模型只能整理、解释已有诊断，不能把“模型自己的猜测”包装成诊断报告结论。

# 17. 轻量 Agent Loop

Agent Loop 不需要 LangGraph / CrewAI / AutoGen 才能做。

一期直接写清晰可测试的 Loop。

```text
1. Authenticate
2. Create AgentRun
3. Load recent session
4. Route intent
5. Build minimal structured context
6. Build system prompt
7. Call model
8. If tool_calls:
      validate tool name
      validate max tool rounds
      inject ToolContext
      execute read-only tool
      append structured result
      call model again
9. Response Guard
10. Stream final answer
11. Persist messages
12. Persist model/tool trace
```

硬限制：

```text
MAX_TOOL_ROUNDS = 2
MAX_TOOLS_PER_ROUND = 3
MAX_TOTAL_TOOL_CALLS = 5
```

如果超过：

```text
AGENT_TOOL_BUDGET_EXCEEDED
```

不要无限循环。

# 24. 学生问答 System Prompt 规范

核心规则：

```text
你是学校学生智能问答助手。

你的首要原则：
1. 只能根据系统提供的真实结构化数据回答学生个人成绩问题。
2. 不允许捏造考试、分数、排名、题目、诊断结论。
3. 数值以 Tool/Context 提供的数据为准，不自行重新计算复杂统计。
4. BASIC 权益下，不得推断薄弱知识点、失分原因、学习能力或诊断结论。
5. 如果用户问“为什么”，但系统只提供客观丢分数据，应明确区分：
   - 已知事实；
   - 系统当前没有的诊断结论。
6. DIAGNOSIS 权益下，只能复述或解释正式诊断报告存在的结论。
7. 不得读取、猜测或暴露其他学生的数据。
8. 默认回答简洁、自然、像正常老师/学习助手，不输出内部 Tool、SQL、JSON、Prompt、trace。
9. 如果数据不足，直接说明缺少哪类数据，不要编。
10. 如果存在多次考试，明确考试名称，避免把不同考试混在一起。
```

回答风格：

```text
先结论
再 2~4 个最重要事实
必要时给下一步
```

不要默认长篇作文。

# 25. Answer Guard

模型生成后增加轻量守门层。

检查：

```text
是否出现其他学生信息
是否出现 Context 中不存在的具体数字
BASIC 是否出现诊断性措辞
DIAGNOSIS 的结论是否能映射到 report evidence
是否把 rank_delta 正负说反
是否把不同考试混淆
```

一期可以先实现规则 + evidence 检查，不需要再调用一个大模型。

示例敏感词规则仅作辅助：

```text

基础不扎实
粗心
理解不够
能力不足
学习习惯
掌握不牢
```

BASIC 下出现这些词不一定全部禁止，但凡是“对学生做诊断”的句子必须有允许的数据来源。

# 61. 推荐的 Agent 请求实例

用户：

> 我这次数学是不是退步了？

Router：

```json
{
  "intent": "SCORE_TREND",
  "subject": "数学"
}
```

Context Plan：

```json
{
  "need_latest_exam": true,
  "need_history": true,
  "need_rank": true
}
```

Service：

```json
{
  "current": {
    "exam": "期中考试",
    "score": 86,
    "rank": 31
  },
  "previous": {
    "exam": "月考",
    "score": 91,
    "rank": 22
  },
  "score_delta": -5,
  "rank_delta": -9
}
```

模型输出：

```text
这次数学比上次退了一些：86 分，比上次少 5 分；年级排名从 22 名到了 31 名，下降了 9 名。
```

这是好答案。

不要：

```text
说明你最近学习状态不好，函数和几何基础不牢。
```

因为没诊断数据。

# 62. DIAGNOSIS 示例

学生问：

> 那为什么数学退步？

如果 BASIC：

```text
从现有成绩数据能确定的是：这次数学比上次少 5 分，主要丢分集中在第 17、20、22 题。
目前没有可读取的学情诊断报告，所以我不能直接判断具体原因。
```

如果 DIAGNOSIS 且报告写：

```text
函数综合题步骤转换不稳定
```

可答：

```text
你的诊断报告把主要原因指向函数综合题的步骤转换不稳定。结合本次小题数据，第 20、22 题丢分也比较集中。
```

第二句话仍需有对应结构化 evidence。
