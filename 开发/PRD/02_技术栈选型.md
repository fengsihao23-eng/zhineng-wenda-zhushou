## 2. 技术选型理由

### 2.1 前端：React + TypeScript

**为什么保留**：
- 现有前端已有 React + TypeScript 资产
- 团队熟悉
- 组件可复用

**一期前端重点**：
- Chat 界面（SSE 流式输出）
- 成绩展示
- 诊断报告查看
- 不需要重写整个管理后台

---

### 2.2 后端：FastAPI

**为什么选择 FastAPI**：
- 原生异步支持（async/await）
- 自动 API 文档（OpenAPI / Swagger）
- 类型提示 + Pydantic 数据校验
- SSE 支持良好
- Python 生态适合 AI 应用
- 性能优于 Flask

**与旧系统关系**：
- 旧系统可能是 Flask + MySQL
- 新系统不删除旧系统，通过 Adapter 共存
- FastAPI 作为新的学生 Agent 主线

---

### 2.3 数据库：PostgreSQL

**为什么从 MySQL 迁移到 PostgreSQL**：
- 更强的 JSON 支持（存储诊断报告 structured_json）
- pgvector 扩展（后续教材 RAG）
- 更严格的数据完整性
- 更好的并发控制
- LISTEN/NOTIFY（实时通知）

**一期策略**：
```text
旧 MySQL
    ↓
Legacy Adapter（只读）
    ↓
新 PostgreSQL（新数据主存储）
```

**不做**：
- 一期不做大迁库
- 通过 Adapter 渐进迁移

---

### 2.4 向量数据库：pgvector

**为什么选 pgvector**：
- PostgreSQL 扩展，无需独立服务
- 运维简单
- 一期不强依赖

**重要原则**：
> "安装 pgvector" ≠ "所有数据都做向量"

**数据分类**：
- **关系型数据**（不向量化）：学生、考试、成绩、排名
- **向量数据**（后续）：教材、讲义、题库语义检索

**一期**：
```sql
CREATE EXTENSION IF NOT EXISTS vector;
```
但不创建 embedding 业务表。

---

### 2.5 ORM：SQLAlchemy 2.x Async

**为什么选择**：
- 异步支持（与 FastAPI 配合）
- 成熟稳定
- 类型提示支持
- 复杂查询能力

**要求**：
- 所有 DB 变更必须通过 Alembic Migration
- 不允许直接在代码里改表结构

---

### 2.6 数据校验：Pydantic v2

**为什么选择**：
- FastAPI 原生集成
- 自动数据校验
- 类型安全
- v2 性能提升显著

**使用场景**：
- API Request/Response
- Tool 参数校验
- Agent Context 结构
- 配置文件

---

### 2.7 缓存/队列：Redis

**一期用途**：
1. Session / Refresh Token 辅助
2. Agent 临时状态
3. Rate Limit
4. Job Queue（异步任务）
5. 数据同步锁
6. 短时成绩查询 Cache
7. SSE 状态
8. 防重复提交 Idempotency Key

**不做**：
- 不把关键业务唯一副本只放 Redis
- 所有持久化数据必须落 PostgreSQL

---

### 2.8 网关：Nginx

**职责**：
- TLS 终止
- 反向代理
- 静态文件服务
- SSE 长连接支持

**路由**：
```nginx
/              → web
/api/          → api
/api/v1/chat/* → api SSE (特殊配置)
/uploads/      → controlled static
```

**SSE 关键配置**：
```nginx
proxy_buffering off;
proxy_cache off;
proxy_read_timeout 300s;
```

---

### 2.9 部署：Docker Compose

**一期服务**：
```yaml
services:
  web:        # React 前端
  api:        # FastAPI 后端
  worker:     # 异步任务 Worker
  postgres:   # 数据库
  redis:      # 缓存/队列
  nginx:      # 网关
```

**不做**：
- 一期不上 Kubernetes
- 不引入过多基础设施（Neo4j、Weaviate、n8n 等）

---

### 2.10 AI 层：自研 Model Gateway

**为什么不直接用 LangChain / LlamaIndex / Dify**：
- 本项目有强业务数据模型
- 需要细粒度学生权限控制
- 需要 BASIC / DIAGNOSIS 业务权益
- 通用 LLM 平台开箱即用解决不了

**自研核心组件**：
```text
ModelGateway         # 统一模型调用入口
  ├── Provider Adapter    # 多厂商适配
  ├── Circuit Breaker     # 熔断降级
  ├── Retry Logic         # 重试策略
  └── Usage Tracking      # Token 统计

PromptRegistry       # Prompt 版本管理

Tool Registry        # Tool 注册与权限

Agent Loop           # 轻量循环（非 LangGraph）

Response Guard       # 最后一道防线
```

**可以借鉴**：
- OpenTutor 的 Context Builder 设计
- LiteLLM 作为 Provider 内部实现之一
- 但 ModelGateway 接口必须是我们自己的

## 3. 新旧路线冲突处理

### 3.1 问题

旧接管文档曾建议：
> "先保留 Flask + MySQL"

最新阶段计划：
> React + FastAPI + PostgreSQL + pgvector

### 3.2 解决策略

```text
旧系统 = 业务资产 + 数据源 + 迁移来源
新系统 = 新 AI / 学生智能体主线
```

**不是直接删除旧系统**

### 3.3 迁移方式

```text
Old MySQL / Old API
        │
        ├── Legacy Adapter（只读旧数据）
        │
        ├── Data Sync（定时同步）
        │
        └── Migration Jobs（渐进迁移）
                ↓
       New PostgreSQL
                ↓
        Student Agent
```

**阶段策略**：
1. **第一阶段**：新系统通过 Adapter 只读旧数据
2. **第二阶段**：数据双写（旧 MySQL + 新 PostgreSQL）
3. **第三阶段**：验证稳定后，新 PostgreSQL 成为 Source of Truth

**避免**：
- "大迁库 + 大改接口 + Agent 新功能" 同时发生

## 4. 不引入的技术

### 4.1 一期明确不用

| 技术 | 为什么不用 |
|---|---|
| LangChain | 过度抽象，不适合强业务逻辑 |
| LangGraph | 一期不需要复杂 Multi-Agent |
| Dify | 不适合直接做产品换皮 |
| RAGFlow | 一期不依赖 RAG |
| Neo4j | 一期没有知识图谱需求 |
| Weaviate | 一期没有向量检索需求 |
| Flowise | 不需要可视化 Workflow |
| n8n | 不需要低代码自动化 |

### 4.2 后续可能引入

| 技术 | 引入时机 |
|---|---|
| RAGFlow | V3 教材 RAG（作为独立服务） |
| Neo4j | V5 知识点掌握图谱 |
| Kubernetes | 多校部署扩展 |

---

## 5. 技术决策原则

1. **优先复用现有资产**（前端、试卷业务）
2. **选择成熟稳定技术**（FastAPI、PostgreSQL、Redis）
3. **避免过度工程**（不为了炫技引入复杂技术）
4. **保持可替换性**（Provider Adapter、Knowledge Adapter）
5. **关注运维成本**（Docker Compose 优于 K8s）
6. **优先解决业务问题**（权限、数据准确性）而非技术问题

---

## 6. 技术风险与应对

| 风险 | 应对 |
|---|---|
| FastAPI 异步复杂度 | 团队培训，代码规范 |
| PostgreSQL 迁移成本 | 渐进迁移，Adapter 缓冲 |
| 自研 Agent 层维护成本 | 借鉴 OpenTutor，保持简单 |
| 模型厂商稳定性 | Provider 多厂商 + Fallback |
| SSE 兼容性 | 降级 Polling（备选） |
